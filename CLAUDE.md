# Claude Development Guidelines

## Project Overview

`@postalsys/certs` is a Node.js library that manages Let's Encrypt (ACME) TLS
certificates: automatic acquisition, renewal, and storage via the ACME protocol.
Certificates, private keys, and ACME account data are stored in Redis. It
supports ACME HTTP-01 challenges and CAA record validation.

It is written in TypeScript under `src/` and published to npm as
`@postalsys/certs` as a dual package: ES modules in `dist/esm/` and CommonJS in
`dist/cjs/`, each with its own type declarations. It is consumed by other Postal
Systems projects (notably EmailEngine, through `require()` inside a pkg binary).

## Project Structure

- `src/certs.ts` - the package entry point. Main `Certs` class: ACME account
  setup, domain validation, certificate acquisition/renewal, renewal information,
  and the HTTP-01 challenge route handler. Also exports `isRenewalDue`,
  `nextRenewalTime`, `renewalThreshold`, `AcmeError` and the public types
- `src/acme-client.ts` - `AcmeClient`: the RFC 8555 client, plus RFC 9773 renewal
  information. Transport-free; it is handed a request function
- `src/jose.ts` - public JWK export, RFC 7638 thumbprints and flattened JWS signing,
  all on `node:crypto`
- `src/der.ts` - a minimal DER writer and reader: builds the PKCS#10 certificate
  signing request, and reads the serial number and Authority Key Identifier that an
  RFC 9773 `certID` is made of. Node has no CSR builder and no access to certificate
  extensions, which is the only reason this file exists
- `src/acme-challenge.ts` - `AcmeChallenge` class (the module's only runtime
  export, a default export): stores and resolves pending HTTP-01 challenge tokens
  in Redis (msgpack-encoded, TTL-expired)
- `src/acme-request.ts` - `createAcmeRequest(dispatcher)`: the request function the
  ACME client sends every exchange through. undici `fetch`, so the caller's
  `dispatcher` option (a proxy agent) covers every ACME exchange. Returns
  `{statusCode, headers, body}` with lower-cased headers and the body parsed as JSON
  when it parses; it never throws on an error status, because deciding what is
  retryable is the client's job
- `src/settings.ts` - `Settings` helper: small Redis hash get/set abstraction.
  EmailEngine imports it directly (`@postalsys/certs/lib/settings`) and builds one
  without a Redis client just to call `getKey()`, so `redis` stays optional
- `src/msgpack.ts` - thin `@msgpack/msgpack` wrapper that keeps the call-site
  contract of the deprecated `msgpack5` it replaced (Buffer in/out, undefined
  properties omitted, trailing bytes ignored)
- `src/tools.ts` - Shared helpers: `normalizeDomain`, `toAsciiDomain`,
  `generateKey`, `parseCertificate` (via the built-in `crypto.X509Certificate`),
  `validationErrors`, and the renewal timing (`renewalThreshold`,
  `nextRenewalTime`, `isRenewalDue`, `renewalInfoState`)
- `src/types.ts` - public data shapes shared by the modules (`CertificateData`,
  `ErrorRecord`, `RenewalInfoRecord`, `Logger`, `TimeValue`)
- `src/vendor-types.d.ts` - minimal ambient declarations for `punycode.js`, which
  ships without types
- `src/package-info.ts` - generated by `scripts/build.js` from `package.json`
  (`name`, `version`, `authorEmail`). Gitignored and regenerated by `npm run build`
  and `npm run typecheck`. Never import `package.json` from `src/`
- `scripts/build.js` - the build: generates `src/package-info.ts`, runs `tsc` with
  `tsconfig.esm.json` and `tsconfig.cjs.json`, writes a `package.json` with the
  module format into each output directory, and rewrites CommonJS modules that only
  have a default export so `require()` returns the class itself
- `scripts/pkg-smoke.js` - `npm run test:pkg`, see Platform constraints
- `scripts/mutation-test.js` - `npm run test:mutation`, see Testing
- `dist/` - build output, gitignored; it is what gets published (`src/` is not)
- `test/` - TypeScript tests (`*-test.ts`). `test/helpers/` holds the mocks and
  fixtures, `test/package/` checks the built `dist/` output
- `examples/test.js` - illustrative usage example (ES module, imports the package
  by name). Type-checked against the built declarations by
  `test/package/examples-test.ts` (`tsconfig.examples.json`)

### Storage layout

A certificate record is split across Redis fields on purpose. `SIDE_FIELDS` in `src/certs.ts`
(`privateKey`, `lastCheck`, `lastError`, `renewalInfo`) each get their own field; everything else is
merged into one `domain:<d>:data` blob by a read-then-write. That merge is only safe under the
per-domain operation lock, so anything written from a path that does not hold the lock has to be a
side field. Renewal information is refreshed in the background, which is exactly why it is one.

## Technology Stack

- **Runtime**: Node.js 20 or newer (`engines.node`); CI tests on 20, 22, 24 and latest.
- **Language**: TypeScript (`tsconfig.base.json`: strict, `exactOptionalPropertyTypes`,
  `noImplicitOverride`, `erasableSyntaxOnly`, `isolatedModules`), compiled twice from
  the same sources. The tsconfig files are shared with nodemailer and imapflow.
- **ACME**: in-house (`src/acme-client.ts`), on `node:crypto` only; HTTP through
  `undici` (`src/acme-request.ts`)
- **Storage**: Redis via an `ioredis` client (injected by the caller; typed as the
  `RedisClient` of `ioredfour`)
- **Distributed locking**: `ioredfour`
- **Validation**: `joi`
- **Serialization**: `@msgpack/msgpack`, behind `src/msgpack.ts`
- **Logging**: `pino` (caller may inject a pino-compatible logger)
- **Domain handling**: `punycode.js`
- **Testing**: Node.js test runner (`node:test`) through `tsx`, coverage with c8

`ioredis` and `express` are devDependencies only (used by tests and examples);
they are not runtime dependencies of the library.

## Engine target and module format

- TypeScript `target: ES2022` with `lib: ES2023`. `@types/node` is pinned to the 20.x
  line (see `.ncurc.cjs`) so the compiler rejects APIs that do not exist on Node 20.
- Source uses ES module syntax and is compiled twice from the same files:
  `tsconfig.esm.json` (`module: nodenext`) into `dist/esm/` and `tsconfig.cjs.json`
  (`module: commonjs`) into `dist/cjs/`. Because every file must compile both ways,
  code under `src/` must not use `import.meta`, `require`, `module`, `exports`,
  `__dirname`, `__filename`, top-level `await`, or JSON imports.
- `erasableSyntaxOnly` is on: no enums, no namespaces with runtime code, no
  parameter properties, no decorators. Use `as const` objects instead of enums.
- `exactOptionalPropertyTypes` is on. Every optional property of a public interface
  is declared with an explicit `| undefined`, so a consumer compiling with that flag
  can still pass a value that may be undefined (`test/package/consumer/` checks it).
- Relative imports always carry the `.js` extension (`'./tools.js'`).
- Node builtins are imported with the `node:` prefix. Use a default import
  (`import crypto from 'node:crypto'`) when the whole module is used.
- Tests are ES modules too (`.ts`, run through `tsx`). They may use `import.meta.url`.

## Export shapes

The CommonJS build keeps the exact runtime shape the pre-TypeScript `lib/*.js` files had,
because consumers deep-import them: EmailEngine `require('@postalsys/certs/lib/settings')`,
https-front `require('@postalsys/certs/lib/tools')`.

- `package.json` `exports` maps `.` to both builds and `./lib/*` (with or without
  `.js`) to the matching file under `dist/`, and `typesVersions` does the same for the
  declarations. `main` and `types` point at the CommonJS build.
- `src/acme-challenge.ts` used to be `module.exports = AcmeChallenge`. It has exactly
  one runtime export, `export default`, and the build rewrites its CommonJS output so
  `require()` returns the class itself (a non-enumerable `.default` alias is kept for
  transpiled default imports). It must not gain other runtime exports; type exports
  are fine. Every other module uses named exports only; `MIXED_EXPORT_MODULES` in
  `scripts/build.js` is empty, and the build fails if a module mixes the two.
- `test/package/package-test.ts` pins every module's export names and kinds for both
  builds (`MODULE_SHAPES`). Removing or retyping an export there is a breaking
  change; a new export is added to the table.

## Testing

- Tests live in `test/` and are named `*-test.ts`; `npm test` runs every one of them,
  through `tsx`. Helpers under `test/helpers/` are not run as tests.
- `npm test` builds first (`pretest`), because `test/package/` loads the built `dist/`
  output through the `exports` map the way an installed copy is loaded.
- Tests use `describe`/`it` from `node:test` and `assert` from `node:assert/strict`.
  The tests are loosely typed on purpose (mock Redis and transports cast through `any`,
  instance methods monkeypatched); the type-aware lint rules apply to `src/` only.
- Tests do not require a live Redis server: `test/helpers/mock-redis.ts` provides
  an in-memory mock. New tests should use it rather than connecting to Redis.
- `test/helpers/mock-acme-server.ts` is an in-memory ACME server that speaks the
  transport contract of `src/acme-request.ts`, so the whole issuance flow runs
  without a socket. It verifies JWS signatures, nonces and the `url` header field,
  and it is modelled on **Boulder**, not on a lenient reading of the RFC:
  finalize is accepted only while the order is `ready`, issuance is asynchronous, and
  problem documents carry their real HTTP status. Both behaviours are what the
  previous `@root/acme` based implementation got wrong, so keep them.
- `test/helpers/test-ca.ts` is a small X.509 CA, so the mock server can hand back a
  certificate that `crypto.X509Certificate` parses and that carries the extensions
  the renewal information code reads. Its DER writing is deliberately independent of
  `src/der.ts`: two implementations that have to agree catch an encoding mistake that
  one shared implementation would hide. Do not merge them.
- `test/msgpack-test.ts` pins the stored wire format against hex fixtures produced
  by the original `msgpack5`. Redis keeps certificate and ACME account records
  indefinitely, so any change to serialization must still decode those fixtures
  and re-encode them to identical bytes. Do not re-record them to make a test pass.
- Seeded fuzzing (`test/helpers/fuzz.ts`): `test/der-fuzz-test.ts` checks the DER
  reader against certificates from the independent test CA and against truncated or
  corrupted DER (only der.ts's own errors, never a TypeError or RangeError), and CSRs
  for random domain lists; `test/tools-fuzz-test.ts` checks that `normalizeDomain` is
  a fixpoint, the bounds of `parseRetryAfter`, that renewal timing never yields NaN
  and stays under the backstop, and msgpack round trips; `test/acme-client-fuzz-test.ts`
  corrupts CA responses (bodies, fields, headers, status codes) and requires every
  order to end in a certificate or an `AcmeError`, every presented challenge to be
  removed, and no unhandled rejection. CA responses are untrusted input: a malformed
  one has to become an `AcmeError`, never a TypeError. `FUZZ_SEED` and
  `FUZZ_ITERATIONS` control a run; a failure names its seed and case. Raise
  `FUZZ_ITERATIONS` for a soak run after touching `src/der.ts` or `src/acme-client.ts`.
- `npm run test:mutation` (`scripts/mutation-test.js`) applies one-operator mutants to
  `src/der.ts`, `src/tools.ts`, `src/jose.ts`, `src/acme-client.ts` and `src/msgpack.ts`
  in private copies of the repository and lists the mutants no test catches. Not part
  of CI; run it after larger changes to those files (`--file <path>` limits it to one
  file) and either add a test for a surviving mutant or confirm it is equivalent.
- `test/package/` checks the build: export shapes of both formats, the exports map,
  that every CommonJS module is reachable from the entry through static `require()`
  calls (what pkg bundles), a consumer type-checked against the shipped declarations
  (`test/package/consumer/`, excluded from the main tsconfig), and the examples.
- For live testing against a real CA, `examples/test.js` serves the challenge on port
  7003 for `localdev.kreata.ee`, which an SSH reverse tunnel
  (`ssh -R 7003:localhost:7003 kreata.ee`) forwards from that host's nginx.
- Always run `npm test` and confirm it is green before committing.

## Platform constraints (important)

Downstream consumers, EmailEngine above all, bundle this library into a single
self-contained binary with **`@yao-pkg/pkg`** (a maintained fork of `vercel/pkg`).
That binary snapshots a **CommonJS** module graph and cannot load ES modules, and
the DigitalOcean one-click images update EmailEngine but never the Node.js under
it. Two rules follow:

- **Node.js 20 is the minimum.** Runtime code, tests and tooling must work on
  Node 20, 22 and 24 (`engines.node` is `>=20.0.0`).
- **The CommonJS build and everything it reaches must be genuinely CommonJS-loadable.**
    - Keep the dual build. Never drop the CommonJS output or make the CommonJS entry
      depend on ES-module-only syntax.
    - `require()` of the package and of every runtime dependency must work with
      `--no-experimental-require-module`. Node 22+ (and 20.19) load ES modules
      through `require()` by default, which hides an ESM-only dependency until the
      pkg binary fails. A CommonJS entry that only wraps a dynamic `import()` does
      not count.
    - Never add or upgrade to an ESM-only dependency, nor to one that needs a newer
      Node than 20. Pin the last compatible major in `.ncurc.cjs` (`reject` or
      `target`) with a comment giving the reason, the way `undici` and `pino` are
      pinned there. A `"type": "module"` package with a `require` condition in its
      `exports` (ioredfour) is a dual package and is fine.
    - Keep `require()`/`import` paths static so pkg can trace the graph. pkg does
      not resolve the `exports` map at build time, so a deep import such as
      `lib/settings` is found inside the binary only because the entry already
      requires that file; every module has to stay reachable from `src/certs.ts`
      (a package test checks this).

**How to check:** `npm run test:cjs` builds `dist/`, then
`test/package/cjs-smoke.cjs` requires the CommonJS entry and the deep imports under
`NODE_OPTIONS=--no-experimental-require-module` and exercises every runtime
dependency. It is plain JavaScript on purpose: tsx's loader would transpile an ES
module dependency and mask the failure. `npm run test:pkg` goes one step further:
it packs the library, installs the tarball into a temporary project, builds a
`@yao-pkg/pkg` binary (`node24` target, as EmailEngine builds) and runs the same
smoke test inside it. CI runs `test:cjs` on Node 22 and later, and `test:pkg` in
its own job. Run both after any dependency change.

**pino and real-require.** pino depends on `real-require`, whose `realImport()` is a
dynamic `import()`. pino loads it only from `lib/transport-stream.js`, inside the
worker thread a transport runs in, so it is reached only when a logger is built
with the `transport` option. This library never does: it calls `pino()` with
defaults or `pino({ enabled: false })`, or uses the logger the caller injects.
Keep it that way; configuring a pino transport here would put a dynamic
`import()` on the runtime path.

## Dependency Management

- Dependencies are refreshed with `npm run update`, which removes
  `node_modules` and `package-lock.json`, runs `ncu -u`, and reinstalls.
- The ACME implementation has no dependencies of its own. Certificate issuance runs
  on `node:crypto` and `undici`, and must stay that way: pulling in an ASN.1 or JOSE
  library to add a feature is how this package ended up on an abandoned stack the
  first time.
- Update policy lives in `.ncurc.cjs`:
    - `undici` stays on the 7.x line (8.x needs Node 22.19+ and EmailEngine keeps a
      Node 20 floor), and `pino` takes patch updates only (pino 10.4 crashes inside a
      pkg binary). `.ncurc.cjs` has the full rationale.
    - `@types/node` stays on the 20.x line, and `typescript` takes minor updates only
      (typescript-eslint's peer range excludes TypeScript 7).
    - `ioredis` follows latest. This library never creates a Redis client, it uses
      the one the caller injects, so `examples/test.js` tracks the major consumers
      (EmailEngine) actually pass in.
    - `express` is rejected from auto-update and kept on the 4.x line.
- devDependencies are pinned to exact versions (no `^` or `~`).
- After running `npm run update`, run `npm test` and review `npm audit`. Runtime
  dependencies must remain CommonJS-compatible (see Platform constraints), so
  also run `npm run test:cjs` and `npm run test:pkg`; do not let an update pull in
  a pure-ESM major.

## Release Process

- Releases are automated with **release-please** (`.github/workflows/release.yaml`).
  Merging the release PR tags a version, generates the changelog, and publishes
  to npm with `npm publish --provenance`. `npm ci` runs the `prepare` script, which
  builds `dist/`, so build output is never committed.
- Commit messages drive releases, so use **Conventional Commits**:
    - `fix:` -> patch release
    - `feat:` -> minor release
    - `feat!:` / `fix!:` or a `BREAKING CHANGE:` footer -> major release
    - `chore:`, `docs:`, `test:`, `ci:`, `refactor:` -> no release
- Only `fix:`/`feat:` commits produce a release, so use them for user-facing
  runtime changes.

## CI / GitHub Actions

- `test.yaml` - on pushes to `master` and PRs: `npm run lint`, `npm run format:check`
  and `npm test` on Node 20, 22, 24 and latest (Node 24 runs `npm run test:coverage`
  instead), `npm run test:cjs` on Node 22 and later, and a `pkg` job running
  `npm run test:pkg`.
- `release.yaml` - release-please + npm publish on pushes to `master`.

After pushing, check the workflow runs (e.g. `gh run list --branch master`) and
report their status. If a run fails for an unrelated infrastructure reason (a
checkout reporting "account suspended", HTTP 403, or other auth/infra errors
unrelated to the change), check https://www.githubstatus.com/ for an active
GitHub incident before assuming the failure is caused by the code.

## Code Style Rules

- Never use emojis in code or documentation; use printable ASCII only.
- Use a single hyphen-minus (`-`) as a dash in user-facing strings. Never use
  double hyphens (`--`), em dashes, or en dashes.
- Formatting follows `.prettierrc` (4-space indent, single quotes, 160-column
  width, no trailing commas, `lf` line endings, `arrowParens: 'avoid'`).
- Linting follows `eslint.config.js`, the shared Postal Systems flat config with
  typescript-eslint (`../nodemailer/eslint.config.js` is the canonical form; `src/`
  also gets the type-aware rules: floating and misused promises, unnecessary type
  assertions, deprecated APIs). Keep it identical to the other repos except for the
  "Repo-specific" block at the end, where `no-await-in-loop` is off (sequential ACME
  polling and retries) and `no-bitwise` is off for the DER code.
- Every options object a public method reads has an exported interface, and every
  optional property carries `| undefined`.
- Before committing code changes: `npm run format`, `npm run lint`, `npm test`.
- When composing git commit messages, do not include Claude as a co-contributor.
- For commits that do not change runtime behavior (docs, comments, CI/workflow
  tweaks, formatting), append `[skip ci]` to the commit message to avoid
  triggering the GitHub Actions workflows. Exception: do not add `[skip ci]` to
  commits using a `fix:` or `feat:` prefix - those must run so the release
  workflow is triggered.
